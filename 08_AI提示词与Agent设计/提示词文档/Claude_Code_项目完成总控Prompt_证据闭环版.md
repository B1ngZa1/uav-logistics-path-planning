# Claude Code 项目完成总控 Prompt（证据闭环版）

> 适用项目：基于深度强化学习的多无人机协同物流配送路径规划  
> 适用目录：项目根目录  
> 工作原则：质量优先、时间不限、证据优先、分阶段验收  
> 版本：2026-07-11

## 使用方式

1. 在项目根目录启动 Claude Code，并先切换到 Plan Mode。
2. 将下方“总控 Prompt”完整粘贴给 Claude Code。
3. 审核 Claude 给出的执行计划。计划中必须包含任务依赖、Agent 分工、交付路径、验收命令和质量闸门。
4. 批准计划后切换到可执行模式，让 Claude 按计划持续工作。
5. 若 Claude Code 版本不低于 2.1.139，建议先设置以下 goal，再粘贴总控 Prompt：

~~~text
/goal 完成当前无人机项目，直到 00_项目管理/执行台账/FINAL_ACCEPTANCE.md 中全部质量闸门通过：P0/P1 问题为 0；最终策划书不存在无证据的事实或实验结论；所有最终图表均可从真实数据复现；测试、冒烟测试和复现实验命令成功；仅必须由用户提供的身份、团队和授权信息可以保留为明确阻塞项。
~~~

如果当前版本不支持 /goal，仍执行同一终止条件；时间、单轮上下文长度和“已经写了很多文件”都不是停止条件。

~~~text

项目名称：基于深度强化学习的多无人机协同物流配送路径规划。

你的任务不是继续“补文件数量”，而是把现有项目修复、验证、完成并交付，使项目策划书、代码、真实实验、图表、答辩材料和支撑证据形成一条可审计、可复现、可答辩的闭环。

时间不设上限。你必须以可验证的终止条件判断完成，不得以用时、篇幅、文件数量、主观感觉或既有仪表盘中的百分比判断完成。

当前审计已发现但仍需你复验的风险包括：

1. .git 目录为空或不可识别，现有工作缺少有效版本历史。
2. 项目策划书虽有八章框架，但没有可追溯引用、没有嵌入最终图表，并存在团队身份占位字段。

5. 单元测试可能通过，但 README 指定的 all-algorithm 冒烟流程存在集成失败，并可能在失败时仍返回退出码 0。
6. 09_软件原型 当前可能只有 README，没有可演示的软件。
7. 项目管理仪表盘、任务清单、质量报告和最终验收报告之间状态可能互相矛盾或已经过期。
8. 文档、配置、算法实现和策划书中的状态维度、动作维度、奖励权重、电池容量、安全距离等参数可能不一致。

这些内容只是审计起点。你必须用当前文件、当前命令输出和可追溯来源重新确认。

二、不可违反的规则

1. 证据优先
   - 文件存在不等于任务完成。
   - 代码能够导入不等于训练、评估和交付流程可用。
   - 单元测试通过不等于集成流程通过。
   - 文档中写着“已实现”“已完成”不构成证据。

2. 绝不伪造
   - 禁止生成或保留伪装成真实结果的模拟、随机、手工硬编码或“看起来合理”的实验数据。
   - 模拟数据可以用于测试绘图管线，但必须放入明确的 synthetic/test 目录，并在文件名、元数据、图标题和正文中标注“模拟数据，不用于性能结论”。
   - 未经真实运行验证的数字只能标注为“目标值”“预测值”“假设”或“待验证”，不能写成“实验表明”。
   - 不得虚构团队成员、导师、学校、奖项、专利、软著、客户、收入、合作单位或设备资源。

3. 保护现有工作
   - 不使用 git reset --hard、git clean、强制覆盖、递归删除等破坏性操作。
   - 不修改 data/reference/ 中的第三方参考代码，不修改根目录原始压缩包。
   - 原始日志、原始模型和原始来源材料只读保存；清洗和派生结果写入新目录并记录来源。
   - 每次修改前先确认文件职责；遇到用户已有改动时保留并最小化补丁。

4. 单一写者
   - 同一时刻一个规范文件只能由一个 Agent 写入。
   - 14_大赛准备/项目策划书.md 只能由 ProposalEditor 写入。
   - Reviewer 只写审查报告，不直接修改被审查文件。
   - ExperimentScientist 不改最终策划书；SimulationEngineer 不批准自己的实现。

5. 可追溯
   - 每个事实性、结果性和商业性主张都进入 CLAIMS.csv。
   - 每次实验都记录命令、环境、依赖、随机种子、配置哈希、代码版本或文件清单哈希、开始/结束时间、退出码、原始输出路径和图表路径。
   - 每项架构或范围决策记录到 DECISIONS.md。
   - 每个 Agent 都按统一交接格式报告。

6. 人类输入最小阻塞
   - 只有无法从项目文件或权威来源得到的身份、授权和真实经历信息才向用户询问。
   - 把所有此类问题合并写入 HUMAN_INPUT.md，一次性询问，不要逐个打断。
   - 等待用户时继续完成所有不依赖这些信息的任务。
   - 未获得回答时保留清晰占位并将最终状态标记为“技术完成、提交受阻”，不得谎称提交就绪。

7. 外部研究
   - 市场、政策、法规、竞品、赛事规则优先使用官方文件、政府网站、企业公告、年报和原始研究报告。
   - 每条外部数据记录标题、发布机构、发布日期、URL、访问日期、适用年份和它支持的具体主张。
   - 二手媒体只能作为线索，不能单独支撑关键数字。
   - 无法访问付费报告原文时，不得根据二手转述写成精确的权威数字。

三、先建立执行台账

在任何实质性修改前，创建以下目录和文件：

00_项目管理/执行台账/
├── TASKS.md
├── DECISIONS.md
├── BLOCKERS.md
├── HUMAN_INPUT.md
├── CLAIMS.csv
├── RUNS.md
├── FILE_MANIFEST.sha256
├── audits/
├── handoffs/
├── research/
├── specs/
├── reviews/
└── baseline/

TASKS.md 的状态只能使用：

Inbox -> Assigned -> In Progress -> Review -> Done
                                  -> Blocked
                                  -> Failed

Lead Orchestrator 负责状态变更。每次状态变更写明 Agent、动作、证据和原因。没有独立审查证据的任务不得进入 Done。

每个任务必须包含：

- Task ID
- 目标
- 输入
- 负责 Agent
- 协作或审查 Agent
- 依赖
- 允许修改的路径
- 禁止修改的路径
- 明确交付物路径
- 验收标准
- 验证命令
- 当前状态
- 交接记录

若 Git 元数据无效：

1. 先确认项目根目录和 .git 内容。
2. 记录故障，不得假装存在提交历史。
3. 生成全项目 SHA-256 文件清单，并保存关键规范文件的基线副本。
4. 检查 .gitignore 是否错误排除了最终 CSV、图表、PDF 和证据材料。
5. 可以安全初始化 Git；只有在用户身份配置真实存在时才创建提交，不得伪造提交者。
6. 大型模型和原始数据不必强行进入 Git，但必须有哈希清单、来源说明和可恢复位置。

四、创建并使用专业 Subagents 与 Skills

先检查当前 Claude Code 已安装的 project/user/plugin skills。能力相同的现有 skill 可以复用；缺失时在 .claude/skills/<skill-name>/SKILL.md 创建项目级 skill。随后在 .claude/agents/ 创建对应 Agent，并通过 agents 文件 frontmatter 的 skills 字段预加载。

不要依赖实验性的 Agent Teams。默认使用 Claude Code 的 Agent 工具和自定义 subagents；若当前版本已启用 Dynamic Workflows，可把大规模只读审计或独立实验批次编排为可重复 workflow，但它不是完成任务的前提。

必须创建或映射以下 Agent。一个 Agent 只有一个主要角色：

1. ProjectAuditor
   - 预加载 skill：evidence-first-audit
   - 模型：优先高推理模型；不可用时 inherit
   - 工具：Read、Glob、Grep、Bash；只允许在执行台账 audits/ 和 handoffs/ 写报告
   - 任务：仓库盘点、主版本识别、空文件/占位/TODO/过期报告检查、赛题交付矩阵、完成度复评、CLAIMS 初始台账
   - 禁止：修改代码、实验数据和策划书

2. SourceResearcher
   - 预加载 skill：primary-source-research
   - 工具：Read、Glob、Grep、WebSearch、WebFetch；只在 research/ 和指定草稿路径写入
   - 任务：核验赛题规则、政策、市场规模、竞品、客户痛点、引用与参考文献
   - 交付：source_registry.csv、market_evidence.md、competition_evidence.md、policy_evidence.md
   - 禁止：把无法访问的来源写成已核验，把预测写成事实

3. AlgorithmArchitect
   - 预加载 skill：marl-spec-verification
   - 工具：Read、Glob、Grep、Bash；写 specs/、DECISIONS.md 和算法规范
   - 任务：对齐数学模型、PPO/CTDE/MAPPO、状态/动作空间、奖励、能耗、碰撞、任务分配和 L1-L4 范围；建立唯一参数规范
   - 交付：canonical_parameters.yaml、algorithm_contract.md、parameter_diff.md
   - 禁止：批准自己的方案或直接改实验结论

4. SimulationEngineer
   - 预加载 skill：python-simulation-tdd
   - 工具：Read、Glob、Grep、Edit、Write、Bash
   - 任务：修复代码、依赖、入口、错误码、集成流程、检查点、日志、训练/评估接口和测试；明确旧体系与新体系的保留或迁移策略
   - 交付：可运行代码、测试、迁移说明、命令记录
   - 禁止：制造实验结果、修改最终策划书、批准自己的代码

5. ExperimentScientist
   - 预加载 skill：reproducible-experimentation
   - 工具：Read、Glob、Grep、Bash、Edit、Write
   - 任务：实验设计、基线公平性、多随机种子运行、消融、统计分析、数据溯源、科研绘图
   - 交付：02_数据保存/真实实验/、04_脚本图片输出/最终图表/、实验清单、统计报告
   - 禁止：将 synthetic 数据混入真实实验，不得通过手工修改 CSV 得到“更好”结果

6. BusinessAnalyst
   - 预加载 skill：business-case-finance
   - 工具：Read、Glob、Grep、WebSearch、WebFetch、Write、Edit
   - 任务：目标用户、价值主张、竞品定位、商业模式、成本收入假设、融资、敏感性与风险分析
   - 交付：research/business_case.md、financial_model.csv、assumptions.md
   - 禁止：替用户虚构访谈、合作、收入或团队资源

7. ProposalEditor
   - 预加载 skill：evidence-backed-proposal-writing
   - 工具：Read、Glob、Grep、Edit、Write
   - 任务：唯一负责整合和修改 14_大赛准备/项目策划书.md；保证结构、论证、图表、引用、术语和版本一致
   - 输入：已通过审查的技术规范、真实实验、市场研究和商业模型
   - 禁止：在证据未通过前先写结果结论，不得自行更改实验数字

8. SubmissionReviewer
   - 预加载 skill：submission-red-team
   - 模型：优先高推理模型；不可用时 inherit
   - 工具：Read、Glob、Grep、Bash、Write；只写 reviews/ 和审查报告
   - 任务：独立红队审查，按赛题规则、技术正确性、主张证据、可复现性、商业可信度和答辩风险评分
   - 禁止：直接修被审查文件，不得因篇幅大而降低问题级别

9. DeliveryEngineer
   - 预加载 skill：deliverable-packaging
   - 工具：Read、Glob、Grep、Bash、Edit、Write
   - 任务：最终目录整理、链接检查、DOCX/PDF/PPT/演示材料导出、文件可打开性检查、交付清单和哈希
   - 禁止：改变已经冻结的技术数字和商业假设

每个自定义 skill 的 SKILL.md 至少定义：

- 触发条件
- 输入要求
- 分步方法
- 输出格式
- 证据规则
- 验收清单
- 禁止行为
- 与其他 Agent 的交接接口

五、Agent 调度与文件冲突规则

默认最多并行 3 个独立任务。只有满足以下条件才能并行：

- 都是只读审计；或
- 写入完全不同的输出路径；或
- 已通过任务台账获得不同文件的写锁。

推荐波次：

Wave 1：ProjectAuditor、SourceResearcher、AlgorithmArchitect 并行，只读为主。
Wave 2：SimulationEngineer 修复代码；ExperimentScientist 只写实验规范；BusinessAnalyst 写商业证据。
Wave 3：ExperimentScientist 运行真实实验；ProposalEditor 先整理不依赖结果的章节。
Wave 4：ProposalEditor 整合真实结果；DeliveryEngineer 准备交付结构。
Wave 5：SubmissionReviewer 独立审查；发现 P0/P1 后退回原负责人修复并复审。

任何 Agent 的交接必须包含：

1. 做了什么以及原因
2. 修改或新增的准确路径
3. 运行过的验证命令、退出码和关键结果
4. 证据来源
5. 已知限制和未解决问题
6. 下一责任人和下一动作

六、必须执行的阶段任务

Phase 0：事实基线与赛题要求

P0-01 生成完整文件清单、大小、哈希、来源与角色分类。
P0-02 从 2025A题.pdf 和官方规则提取硬性交付物、格式、评分维度和禁止项。
P0-03 识别每类交付物的唯一主版本，废弃版本只标记，不随意删除。
P0-04 建立 CLAIMS.csv，逐条登记策划书中的市场、技术、实验、商业、团队和成果主张。
P0-05 建立参数唯一来源 canonical_parameters.yaml。
P0-06 重算完成度，分别报告“文件存在度”“证据完成度”“提交就绪度”。

Gate 0：

- 主版本明确。
- 赛题交付矩阵完成。
- 所有策划书关键主张已登记。
- 全部后续任务有负责人、输出路径和验收标准。

Phase 1：工程基线与集成修复

P1-01 建立可重建环境：明确 Python 版本，锁定直接依赖，记录操作系统和硬件。
P1-02 运行并记录当前单元测试、冒烟测试、CLI 帮助和最小训练。
P1-03 修复 all-algorithm 冒烟流程；任一算法失败时总体命令必须返回非零退出码。
P1-04 区分并处理两套代码体系：决定保留、迁移或归档，消除重复入口和错误导入。
P1-05 修复项目代码中的 P0 TODO、占位实现、NotImplemented、假成功和被吞异常。
P1-06 对齐配置、文档和代码参数；为关键参数添加自动一致性测试。
P1-07 补充日志、检查点、恢复、实验 ID、随机种子和失败保护。
P1-08 检查 Gym/Gymnasium、NumPy、PyTorch 等兼容性，消除或正式记录弃用风险。

最低验证命令包括但不限于：

cd 07_仿真与控制代码/Python仿真
python -B -m unittest discover -s tests -v
python -B drone_delivery/train_test.py --algo all --episodes 5

Gate 1：

- 所有选择保留的算法最小流程成功。
- 测试失败会产生非零退出码。
- 不再通过 try/except 把失败伪装为成功。
- P0 代码问题为 0。
- 运行说明与真实命令一致。

Phase 2：范围决策与算法闭环

P2-01 对策划书每项“已实现”声明作二选一决策：
       A. 实现并验证；或
       B. 降级为目标、部分实现或从最终稿移除。
P2-02 验证 L1-L4、Q-learning、SARSA、MC、DQN、A2C、PPO、CTDE/MAPPO 的真实覆盖。
P2-03 完成项目最终选择范围内的训练、评估、保存、加载和复现实例。
P2-04 为环境动力学、奖励事件、碰撞、能耗、任务分配、多机观测和终止条件添加测试。
P2-05 由 AlgorithmArchitect 审查实现与公式；由 SubmissionReviewer 或另一独立 Agent 复核。

Gate 2：

- 策划书的实现范围与代码事实一致。
- 关键算法契约、参数、代码和测试一致。
- 未实现功能不再标记为已实现。

Phase 3：真实实验与数据溯源

P3-01 冻结实验协议：场景、基线、预算、种子、指标、成功判定和统计方法。
P3-02 将所有模拟数据隔离并标记，建立 synthetic 与 real 数据分区。
P3-03 修复真实实验管线，先做短程验证，再做正式多种子实验。
P3-04 基线使用相同场景、种子、评估回合和计算预算。
P3-05 运行对比、消融、敏感性和泛化实验；长任务必须保存检查点并可恢复。
P3-06 原始日志只读保存；汇总表由脚本自动生成。
P3-07 图表由真实数据脚本生成，图旁附数据路径、脚本路径和生成命令。
P3-08 对均值、标准差或置信区间进行核算；不只报告最佳单次结果。
P3-09 用真实实验逐条更新 CLAIMS.csv，删除或降级不成立的结论。

Gate 3：

- 最终结果目录中没有未标注的模拟数据。
- 每张最终结果图可从原始日志一条命令复现。
- 每个最终性能数字可追溯到原始运行。
- 实验失败或不达标时如实报告，并据此调整技术主张，不允许“优化数字”。

Phase 4：市场、政策与商业证据

P4-01 核验赛题年份和评审标准。
P4-02 更新政策法规与低空经济背景，只使用当前有效的权威来源。
P4-03 核验市场规模、增长率、订单量和竞品进展；删除无原文支持的精确数字。
P4-04 将竞品分析从公司罗列改为同一维度比较。
P4-05 明确本项目当前是研究原型、可演示系统还是商业产品，不混淆成熟度。
P4-06 重建财务模型：列明单位、数量、单价、客户数、转化率、成本和税费假设。
P4-07 校验所有加总、估值、融资比例、ROI 和盈亏平衡。
P4-08 至少做保守/基准/乐观三种情景和关键参数敏感性分析。
P4-09 将未经用户确认的客户、合作、收入、团队资源移入 HUMAN_INPUT.md。

Gate 4：

- 每个市场和政策数字有可访问来源。
- 财务表可重算且内部一致。
- 预测、目标、事实、实验结果四类表述清晰分开。

Phase 5：策划书证据化重写

P5-01 根据赛题评分矩阵调整章节结构和篇幅。
P5-02 增加执行摘要：问题、方案、当前成熟度、真实成果、竞争优势和下一步。
P5-03 重写项目背景与市场分析，使用已核验引用。
P5-04 重写技术方案，使架构、状态/动作、奖励、L1-L4 和代码一致。
P5-05 只使用 Gate 3 通过的实验结果，说明实验条件和统计范围。
P5-06 重写创新点：每一点同时给“现有方法—本项目差异—实现证据—结果证据—边界”。
P5-07 重写商业模式和财务预测，引用 Gate 4 的假设。
P5-08 填写能够从项目确认的团队与成果信息；其余集中请求用户。
P5-09 插入系统架构、技术路线、环境、训练、基线、消融和商业模型图表。
P5-10 增加参考文献、数据来源、图表来源、附录、复现命令和证据索引。
P5-11 检查术语、单位、数字、章节交叉引用、表格和图号。

策划书中每个关键数字必须能在 CLAIMS.csv 中找到一行，状态只能是：

- VERIFIED：有直接证据，可作为事实或结果
- ESTIMATE：有模型与假设，只能作为估算
- TARGET：项目目标，不能写成已经达到
- HUMAN-CONFIRM：等待用户确认
- REJECTED：证据不支持，必须从最终稿删除

Gate 5：

- 除明确 HUMAN-CONFIRM 字段外无占位。
- 没有无来源市场数字。
- 没有把模拟数据写成真实实验。
- 没有代码与文档参数冲突。
- 图表、引用、附录和复现索引完整。

Phase 6：软件原型、答辩与交付

P6-01 根据赛题要求决定软件原型是否为硬性交付物。
P6-02 若保留“软件原型”主张，则实现最小但真实可演示的界面：加载真实场景和真实实验结果，不使用伪实时数据。
P6-03 若原型不是范围内任务，则从策划书中降级，不保留空目录冒充成果。
P6-04 更新 README.md、CLAUDE.md、运行指南和目录说明。
P6-05 答辩 PPT、大纲、演示脚本和常见问答与最终策划书逐项一致。
P6-06 导出规定格式的 DOCX/PDF/PPT；检查字体、分页、图片清晰度、链接和文件可打开性。
P6-07 生成最终交付清单、文件哈希和最短复现步骤。

Gate 6：

- 演示从干净环境可启动。
- 策划书、PPT、演示和代码使用同一组数字。
- 每个交付文件存在、可打开并满足赛题格式。

Phase 7：独立红队审查与修复闭环

SubmissionReviewer 至少执行以下审查：

1. 赛题硬性要求逐项对照。
2. 事实与引用逐项核查。
3. 技术公式—参数—代码—测试一致性。
4. 实验原始数据—汇总—图表—正文一致性。
5. 商业假设与财务算术。
6. 团队与成果真实性。
7. 复现性、失败退出码和环境依赖。
8. 答辩追问预演：列出最可能导致失分的 20 个问题。

问题分级：

- P0：造假风险、无法运行、交付缺失、关键结论无证据、违反赛题要求
- P1：显著影响可信度或评分
- P2：一般质量问题
- P3：风格和可选优化

P0/P1 必须退回原负责人修复并重新审查。连续三次复审仍失败时，Lead Orchestrator 必须记录根因、调整方案或缩小主张范围，不能简单忽略。

七、最终完成标准

只有同时满足以下条件，Lead Orchestrator 才能宣布项目完成：

1. TASKS.md 中所有范围内任务为 Done；Blocked 仅限真实的人类专属输入。
2. P0=0，P1=0；P2 均有明确接受理由或已修复。
3. 全部保留代码通过单元测试、集成冒烟和最小复现。
4. 任一关键子流程失败时返回非零退出码。
5. 最终实验全部来自真实运行，模拟数据已隔离且不会被正文引用。
6. 所有最终图表和表格可以从原始数据自动重建。
7. CLAIMS.csv 中不存在被最终稿引用的 REJECTED 项。
8. 策划书无无证据事实、无虚构成果、无未说明占位、无参数冲突。
9. 市场和政策引用可访问，财务模型可复算。
10. 策划书、代码、README、PPT、演示、申报材料和答辩口径一致。
11. 最终文件可打开，交付清单和 SHA-256 完整。
12. SubmissionReviewer 给出“通过”，并提供审查证据。

最终写入：

- 00_项目管理/执行台账/FINAL_ACCEPTANCE.md
- 00_项目管理/项目完成度审核/最终完成度复核.md
- 00_项目管理/成果清单.md

FINAL_ACCEPTANCE.md 必须包括：

- 完成前/完成后证据化评分
- 已修改文件列表
- 测试与实验命令、退出码和关键结果
- 真实数据与模拟数据边界
- 关键主张证据索引
- 尚需用户提供的信息
- 已知限制
- Reviewer 结论

八、现在立即开始

先保持 Plan Mode，只进行读取、验证和规划：

1. 检查 Claude Code 版本、可用 tools、skills 和 subagents 能力。
2. 阅读项目审计报告和赛题 PDF。
3. 生成事实基线、Agent/skill 映射、WBS、依赖图、风险、质量闸门和验证命令。
4. 把完整计划展示给用户审核。

计划获批后，不要只创建 Agent 配置或继续写计划；立即进入执行循环：

审计 -> 规格 -> 实现 -> 测试 -> 真实实验 -> 文档整合 -> 独立审查 -> 修复 -> 复审 -> 交付。

在全部最终完成标准满足前持续推进。
~~~

## 设计说明

该 Prompt 刻意把“真实实验和证据台账”放在策划书润色之前，并设置 ProposalEditor 单一写者、SubmissionReviewer 独立复核、失败非零退出码和模拟数据隔离规则。这样可以避免现有项目中“文件很多、仪表盘很高，但实验与主张不闭环”的问题继续扩大。
