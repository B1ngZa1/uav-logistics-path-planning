| ---: | --- | --- | ---: | --- |

```

每两周:           T3 → T6
按需:             T7（新增 agent_* 后）
```

## T1 策划书自动更新

### 目标

比对策划书描述与项目实际状态，找出过时内容，生成差异报告并自动修补可修补项。

### 📋 触发指令

```
执行 T1 策划书自动更新，按以下步骤精确操作：

【Step 1：读取策划书】
读取以下文件全文：
- 11_国家级立项申报/01_申报书主文档/项目申报书.md

【Step 2：收集项目实际状态】
逐一读取以下文件，提取关键信息：
- 00_项目管理/成果清单.md → 提取「已完成成果」和「进行中成果」列表
- 00_项目管理/项目进度计划.md → 提取各阶段起止时间和状态
- 06_模型与算法/算法文档/算法设计文档索引.md → 提取已设计的算法清单
- 01_参考文献/参考文献清单.md → 提取参考文献列表
- 01_参考文献/知识库/中文文献完整索引.md → 提取中文文献列表

统计实际数据：
- 列出 07_仿真与控制代码/Python仿真/drone_delivery/ 下所有 agent_* 目录名
- 统计 06_模型与算法/算法文档/ 下的 .md 文件数量（目标 20 篇）
- 统计 01_参考文献/知识库/ 各子目录下的 .md 知识卡片数量
- 统计 04_脚本图片输出/论文插图/ 下的 .png 文件数量（目标 21 张）

【Step 3：逐项比对并生成差异清单】
按以下 6 个维度逐一比对策划书 vs 实际状态：

维度A — 技术方案一致性：
  策划书中提到的算法名（PPO/CTDE/Q-learning/DQN/A2C/Monte Carlo）
  vs drone_delivery/ 下实际存在的 agent_* 目录名。
  检查：策划书提到但代码中不存在的 → 标记 [代码缺失]
        代码中存在但策划书未提到的 → 标记 [策划书需补充]

维度B — 参考文献完整性：
  策划书「参考文献」章节引用的论文列表
  vs 01_参考文献/参考文献清单.md + 知识库/中文文献完整索引.md 的合并列表。
  检查：知识库中有但策划书未引用的重要论文（评分≥B的）→ 标记 [建议引用]
        策划书引用但知识库中无对应卡片的 → 标记 [需补充卡片]

维度C — 预期成果对齐：
  策划书「预期成果」章节列出的成果项
  vs 00_项目管理/成果清单.md 中的实际完成项。
  检查：已完成但策划书未更新为「已完成」的 → 自动修补
        策划书预期但尚未开始的 → 标记 [待启动]

维度D — 时间计划一致性：
  策划书中的时间表（12个月，2026.07-2027.06）
  vs 00_项目管理/项目进度计划.md 的实际进度。
  检查：里程碑时间偏移>1个月的 → 标记 [计划调整]

维度E — 政策引用时效性：
  策划书引用的政策文件（如《无人驾驶航空器飞行管理暂行条例》）
  检查：是否有2025-2026年新出台的低空经济/无人机政策 → 用Web搜索补充

维度F — 占位符检查：
  扫描策划书全文中的 [姓名]、[学院]、[专业]、[成员1] 等占位符。
  列出所有仍存在的占位符 → 标记 [待填写]

【Step 4：输出差异报告】
将比对结果写入 00_项目管理/策划书差异报告_2026-07-13.md，格式：

# 策划书差异报告
> 生成时间: [时间]
> 策划书版本: [原文件顶部版本]

## 1. 技术方案一致性
| 算法 | 策划书状态 | 代码状态 | 差异 | 处理方式 |
|------|-----------|---------|------|---------|
| PPO | 提到 | agent_diy存在 | 一致 | — |
| ... | ... | ... | ... | ... |

## 2. 参考文献差异
[同格式表格]

## 3-6. [其他维度同格式]

## 汇总
- 可自动修补: [数量] 项
- 需人工确认: [数量] 项
- 已自动修补: [数量] 项

【Step 5：自动修补】
对以下类型的差异直接修改策划书（修改前先备份原内容到报告中）：
- 维度C中「已完成但未更新」的成果 → 更新状态为已完成
- 维度B中「建议引用」且评分≥A的论文 → 追加到参考文献列表

对以下类型的差异标记 [待确认] 而不自动修改：
- 维度D的时间计划调整
- 维度A的算法路线变更
- 维度F的个人信息填写
```

## T2 算法代码与设计文档同步检查

### 目标

比对 `06_模型与算法/` 设计文档与 `drone_delivery/` 代码实现中的参数、接口、网络架构，确保三者（文档→配置→代码）完全一致。

### 📋 触发指令

```

【Step 1：提取设计文档中的参数定义】
逐一读取以下 8 个核心设计文档，提取每个文档中以 Markdown 表格形式定义的参数：
- 06_模型与算法/算法文档/状态空间设计.md → 提取 state_dim、各分量维度
- 06_模型与算法/算法文档/动作空间设计.md → 提取 action_dim、动作类型（Discrete/Box）
- 06_模型与算法/算法文档/PPO算法设计.md → 提取 lr, gamma, lambda, epsilon, batch_size, K_epochs, buffer_size
- 06_模型与算法/算法文档/CTDE框架设计.md → 提取 n_agents, communication_dim, centralized_critic 参数
- 06_模型与算法/算法文档/奖励函数设计.md → 提取各奖励分量名称和权重
- 06_模型与算法/算法文档/能耗模型设计.md → 提取能耗系数

【Step 3：逐参数三方比对】

|--------|-----------|-----------|-----------|--------|---------|

- P0（必须修复）：同名参数在任意两处的数值不同
  例：文档写 gamma=0.99 但代码默认 gamma=0.95
- P1（建议修复）：文档描述与代码实现的类型/结构不同
  例：文档说动作空间是 Discrete(8) 但代码实现是 Box(3)
- P2（信息提示）：参数仅在一处定义，其他处未提及
  例：代码中定义了 reward_clip=5.0 但文档中未记录

- Critic 网络：隐藏层维度列表、每层激活函数、输出维度
- 是否使用正交初始化 (orthogonal init)

与设计文档中的网络架构表比对。参考标准：

- Actor 激活: ReLU, 输出: 2*action_dim (mu + log_sigma)
