## 1. 项目概述

### 1.1 项目目标

本项目面向三维空域中的多无人机协同物流配送问题，使用 PPO（Proximal Policy Optimization）学习连续控制策略，并围绕多机避碰、障碍物规避、配送效率、能耗和任务分配开展算法设计与仿真验证。

项目当前定位是“算法与仿真研究平台”，不包含真实无人机、飞控固件、通信链路、硬件在环或实际物流系统部署。

### 1.2 核心任务

一轮任务中，多架无人机在给定三维空域内飞行，输出三维加速度动作，完成随机生成的配送目标，同时尽量减少碰撞和无效飞行。基础训练环境在全部目标完成或达到最大步数时终止。

### 1.3 当前实现状态

| 子系统 | 主要文件 | 状态 | 说明 |
|---|---|---:|---|
| 基础训练环境 | `environment/airspace_env.py` | 可运行 | 当前主训练脚本实际使用的 Gym 环境 |
| PPO 智能体 | `algorithm/ppo_agent.py` | 可运行 | 使用全局拼接状态和联合动作 |
| 三维体素空域 | `environment/airspace.py` | 可运行 | 独立的场景建模、距离场和可视化基础 |
| 城市复杂空域 | `environment/urban_airspace.py` | 原型 | 已建模多类城市障碍物，尚未接入主训练 |
| CTDE 框架 | `algorithm/ctde_framework.py` | 实验性 | 集中式 Critic 已定义，尚未接入 PPO 更新 |
| 能耗模型 | `environment/energy_model.py` | 独立模块 | 基础环境的电量仍为固定占位值 |
| 任务分配 | `algorithm/task_allocator.py` | 独立模块 | 支持贪心、匈牙利和动态重分配，尚未接入环境 |
| 基线与消融 | `experiments/` | 未完成 | 两个脚本仍包含 `TODO` |
| 单元测试 | `tests/` | 通过 | 2026-07-03 实测 19 项通过、1 项警告 |

> **阅读原则**：本指南以源码为准。项目中的论文、方案和旧版指南描述了目标设计，但并非所有设计均已接入当前执行链路。

### 1.4 目标架构与当前主链路

目标架构是 PPO + CTDE：执行时每架无人机根据局部观测决策，训练时集中式 Critic 使用全局状态。当前主训练代码则由单个 PPO Agent 接收全部无人机状态的拼接向量，一次输出全部无人机的联合动作。

当前主链路如下：

```text
config.py
   ↓
AirspaceEnv.reset()
   ↓  全局状态：num_uavs × 11
PPOAgent.select_action()
   ↓  联合动作：num_uavs × 3
AirspaceEnv.step()
   ↓
环境奖励、终止信号、统计信息
   ↓
PPOAgent.store_transition() → compute_gae() → update()
   ↓
模型检查点与训练日志
```

## 4. 配置系统

配置入口为 `Python仿真/config.py`。修改参数后，应同时确认调用脚本是否实际读取该参数。

### 4.1 基础环境参数

| 参数 | 默认值 | 单位/形状 | 实际用途 |
|---|---:|---|---|
| `space_size` | `(100, 100, 50)` | m | X、Y、Z 空域边界 |
| `num_uavs` | `3` | 架 | 无人机数量 |
| `num_targets` | `5` | 个 | 随机配送目标数量 |
| `num_obstacles` | `10` | 个 | 球形障碍物数量 |
| `dt` | `0.1` | s | 仿真时间步长 |
| `max_steps` | `1000` | step | 单回合最大步数 |
| `v_max` | `15.0` | m/s | 合速度上限 |
| `a_max` | `5.0` | m/s² | 每轴加速度上限 |
| `z_min` | `10.0` | m | 最低飞行高度 |
| `z_max` | `50.0` | m | 最高飞行高度 |
| `d_safe_uav` | `10.0` | m | 设计值；当前主环境未读取 |
| `d_safe_obstacle` | `5.0` | m | 设计值；当前主环境未读取 |

`AirspaceEnv` 实际读取的键是 `d_safe`，而 `ENV_CONFIG` 定义的是 `d_safe_uav` 和 `d_safe_obstacle`。因此当前主环境会使用内部回退值 `5.0 m`。如需区分机间和障碍物安全距离，应先统一接口，而不是只改配置文件。

### 4.2 PPO 参数

| 参数 | 默认值 | 说明 |
|---|---:|---|
| `learning_rate` | `3e-4` | Actor/Critic 学习率 |
| `min_learning_rate` | `1e-5` | 计划用于退火下限 |
| `gamma` | `0.99` | 折扣因子 |
| `gae_lambda` | `0.95` | GAE 参数 |
| `clip_epsilon` | `0.2` | PPO 裁剪范围 |
| `entropy_coef` | `0.01` | 熵正则系数 |
| `value_coef` | `0.5` | 价值损失权重 |
| `max_grad_norm` | `0.5` | 梯度裁剪 |
| `batch_size` | `256` | 小批量大小 |
| `hidden_dim` | `256` | 首层隐藏维度 |
| `update_epochs` | `4` | 推荐作为每批 PPO 更新轮数 |
| `num_epochs` | `1000` | 当前被误传为每回合 PPO 更新轮数 |

> **重要**：`PPOAgent` 中的 `num_epochs` 表示每次 `update()` 内重复优化的轮数，不是训练回合数。`main_train.py` 和 `run_training.py` 当前把 `PPO_CONFIG['num_epochs']=1000` 传入 Agent，会导致每个回合执行 1000 轮更新。正式训练前应改为读取 `update_epochs=4`。

### 4.3 配置接入情况

| 配置字典 | 当前接入情况 |
|---|---|
| `ENV_CONFIG` | 已接入基础环境和主要训练脚本 |
| `PPO_CONFIG` | 部分接入；调用方把 `learning_rate` 映射为 `lr` |
| `NETWORK_CONFIG` | 未直接接入 `PPOAgent`，网络结构仍在代码中硬编码 |
| `REWARD_CONFIG` | 未接入 `AirspaceEnv._compute_reward()` |
| `TRAIN_CONFIG` | 训练回合、保存和日志间隔已使用；`eval_interval` 未使用 |
| `UAV_CONFIG` | 当前主环境未直接使用 |

## 5. 基础训练环境 AirspaceEnv

### 5.1 初始化与重置

```python
from config import ENV_CONFIG
from environment.airspace_env import AirspaceEnv

env = AirspaceEnv(ENV_CONFIG)
state = env.reset()
```

`reset()` 会随机生成：

- `num_uavs` 个无人机位置，初速度为 0；
- `num_targets` 个配送目标；
- `num_obstacles` 个球形障碍物，半径在 3–8 m 间；
- 全部配送状态和距离历史。

当前随机生成没有执行无碰撞采样，初始位置、目标和障碍物可能重叠。需要严格实验复现时，应增加有效性检查并统一随机种子。

### 5.2 观测空间

每架无人机使用 11 维状态，所有无人机状态按顺序拼接：

| 索引 | 分量 | 维度 | 当前处理 |
|---:|---|---:|---|
| 0–2 | 位置 `(x, y, z)` | 3 | 原始米制坐标 |
| 3–5 | 速度 `(vx, vy, vz)` | 3 | 原始 m/s |
| 6 | 最近未完成目标距离 | 1 | 原始距离 |
| 7 | 最近障碍物表面距离 | 1 | 最小截断为 0 |
| 8 | 最近其他无人机距离 | 1 | 单机时使用空域对角线 |
| 9 | 剩余电量 | 1 | 当前固定为 `0.8` |
| 10 | 配送进度 | 1 | 已完成目标数 / 总目标数 |

默认 3 架无人机时：

```text
state.shape = (33,)
```

基础环境没有调用 `StateEncoder`，因此位置、速度和距离量纲混合。对训练稳定性敏感的实验应先接入归一化。

### 5.3 动作空间

动作是每架无人机的三维加速度：

```text
actions.shape = (num_uavs, 3)
actions[i] = [ax, ay, az]
```

环境按 `[-a_max, a_max]` 裁剪，默认范围为 `[-5, 5] m/s²`。随后执行：

```text
加速度裁剪 → 速度积分 → 合速度约束 → 位置积分 → 空域边界裁剪
```

注意：`PPOAgent.select_action()` 目前又把联合动作裁剪到 `[-3, 3]`，因此策略实际无法使用环境允许的完整加速度范围。

### 5.4 step 接口

```python
next_state, reward, done, info = env.step(actions)
```

| 返回值 | 类型 | 说明 |
|---|---|---|
| `next_state` | `np.ndarray` | 下一时刻全局拼接状态 |
| `reward` | `float` | 所有无人机共享的标量奖励 |
| `done` | `bool` | 全部配送完成或达到最大步数 |
| `info` | `dict` | `delivered`、`collisions`、`step` |

该接口遵循旧版 Gym 的四元组形式，尚未拆分 `terminated` 和 `truncated`。

### 5.5 当前实际奖励

主训练使用 `AirspaceEnv._compute_reward()`，而不是 `config.py` 中的 `REWARD_CONFIG`。实际分量如下：

| 分量 | 条件 | 数值 |
|---|---|---:|
| 进度奖励 | 接近每个未完成目标 | `10 × (前距-现距)/前距` |
| 接近奖励 | 与未完成目标距离 `< 50 m` | `50 × (1-d/50)` |
| 到达奖励 | 与目标距离 `< 10 m` | `+500` |
| 障碍物碰撞 | 进入球形障碍物 | `-50` |
| 障碍物接近 | 未碰撞且距离中心 `< d_safe` | `-5` |
| 机间过近 | 无人机距离 `< d_safe` | `-20` |
| 时间惩罚 | 每架无人机每步 | `-0.1` |
| 全部完成 | 所有目标已配送 | `+1000` |

其中障碍物“接近”判断使用的是到障碍物中心的距离，而不是到表面的距离；这与观测中的 `d_obs` 定义不完全一致。

### 5.6 终止条件

满足任一条件即结束：

1. 所有目标完成；
2. `step_count >= max_steps`。

基础环境当前不会因电量耗尽、越界或碰撞而直接终止。

## 6. 三维体素空域与城市环境

### 6.1 Airspace3D

`environment/airspace.py` 提供独立的三维场景工具。默认空域为 `100 × 100 × 50 m`，分辨率为 `5 m`，体素数组为 `20 × 20 × 10`。

体素编码：

| 值 | 枚举 | 含义 |
|---:|---|---|
| 0 | `FREE` | 自由空间 |
| 1 | `OBSTACLE` | 静态障碍物 |
| 2 | `NO_FLY` | 禁飞区 |
| 3 | `DYNAMIC` | 动态障碍物区域 |

支持：

- 长方体与圆柱体障碍物；
- 多边形禁飞区；
- 球形动态障碍物；
- 配送站与客户起降点；
- 6/18/26 邻域；
- 欧氏距离场；
- 轨迹碰撞检测与三维可视化。

示例：

```python
from environment.airspace import Airspace3D

airspace = Airspace3D({
    "airspace_size": (100, 100, 50),
    "resolution": 5,
})
airspace.create_default_city_scene()
airspace.build()
print(airspace.get_state().shape)
```

该模块通过单元测试，但尚未替代 `AirspaceEnv` 中的随机球形障碍物。

### 6.2 UrbanAirspaceEnv

`environment/urban_airspace.py` 是城市配送原型，默认空域为 `2000 × 2000 × 200 m`，每架无人机 14 维观测，动作仍为三维加速度。

已建模的元素包括：

- 10 栋建筑；
- 河流与两座桥；
- 3 组高压线塔；
- 4 个树木区域；
- 动态飞鸟区；
- 2 个禁飞区；
- GPS 干扰区；
- 动态风雨区；
- 1 个配送中心和 11 个客户点。

单机 14 维观测：

```text
位置3 + 速度3 + SOC1 + 载重1 + 目标距离1
+ 目标方向3 + 最近障碍物距离1 + 配送进度1
```

城市环境使用配置键 `num_drones` 和 `num_delivery_points`，与基础环境的 `num_uavs`、`num_targets` 不同。当前 `num_delivery_points` 不会改变硬编码的配送点列表；每架无人机也会独立遍历同一组配送点，因此暂不等同于真正的多机任务分配。

## 7. PPO 与多智能体框架

### 7.1 PPOAgent

当前 PPO 采用连续高斯策略：

- Actor：`state_dim → 256 → 128 → 64 → mean/log_std`，ReLU；
- Critic：`state_dim → 256 → 128 → 64 → 1`，Tanh；
- 优势估计：GAE；
- 策略目标：PPO clipped surrogate objective；
- 优化器：Actor 和 Critic 各自使用 Adam；
- 梯度裁剪：默认 `0.5`。

默认主训练维度：

```text
state_dim  = num_uavs × 11 = 33
action_dim = num_uavs × 3  = 9
```

这是一种集中式联合策略。状态和动作维度随无人机数量变化，因此不同无人机数量的模型检查点不能直接互载。

### 7.2 模型保存与加载

```python
agent.save("model.pth")
agent.load("model.pth")
```

检查点包含：

```python
{
    "actor": actor_state_dict,
    "critic": critic_state_dict,
}
```

当前检查点不包含优化器状态、配置、归一化统计或训练轮次；`load()` 也未指定 `map_location`。如需可靠续训，应一并保存这些信息。

### 7.3 CTDEFramework

`CTDEFramework` 已实现：

- 将局部状态拼成全局状态；
- 从环境字典构建 11 维局部观测；
- 集中式 Critic；
- 共享奖励；
- 通信范围内的邻机消息。

但 `shared_actor` 仍为 `None`，主训练没有调用 `CTDEFramework`，集中式 Critic 也未参加 PPO 损失计算。因此对外描述时应使用“已完成框架原型”，不能表述为“主算法已采用 CTDE 训练”。

### 7.4 独立奖励模块

项目保留三套独立奖励类：

- `RewardFunction`：目标、碰撞、间距、队形、能耗、时间、平滑、配送 8 类设计，其中队形分量当前未计算；
- `ImprovedRewardFunction`：面向课程学习的密集奖励；
- `EnhancedRewardFunction`：强化方向、接近与到达引导。

`run_improved_training.py` 和 `run_enhanced_training.py` 试图替换环境奖励，但它们从 `info` 读取位置、速度和目标，而基础环境当前的 `info` 不提供这些字段，代码会回退到零向量或默认目标。正式使用前应让环境明确返回训练所需信息。

### 7.5 任务分配

完整任务分配模块支持：

- 订单状态、无人机状态和事件枚举；
- 距离、时间、能耗、紧急度、负载均衡综合代价；
- 容量、电量和时间窗约束；
- 贪心和匈牙利分配；
- 新订单、电量不足、超时风险、故障和周期重优化；
- 自适应算法选择。

当前该分配结果没有进入 `AirspaceEnv.target_positions` 或无人机局部目标。接入时建议把“订单分配”作为高层决策，把 PPO 作为低层连续路径控制器。

### 8.5 训练循环

```python
state = env.reset()
while not done:
    action, log_prob, value = agent.select_action(state)
    actions = action.reshape(env.num_uavs, 3)
    next_state, reward, done, info = env.step(actions)
    agent.store_transition(state, action, reward, done, log_prob, value)
    state = next_state

actor_loss, critic_loss = agent.update(next_value=0)
```

当前实现每个回合结束后更新一次。较长回合会使缓冲区很大；工程化实现可改为固定 rollout 长度，并在未终止时用 Critic 估计 `next_value`。

### 11.1 新增场景

建议在 `config.py` 集中定义：

```python

    "S1": {"num_uavs": 3, "num_targets": 5, "num_obstacles": 0},
```

### 11.2 修改状态空间

修改顺序：

1. 更新环境 `_get_obs()`；
2. 更新 `observation_space.shape`；
3. 更新 `StateEncoder`；
4. 更新 PPO 的 `state_dim`；
5. 更新 CTDE 的 `local_state_dim`；
6. 更新测试、模型命名和文档。

状态维度变化后，旧模型检查点通常不能继续加载。

### 11.3 修改动作空间

保持以下值一致：

- `ENV_CONFIG['a_max']`；
- `AirspaceEnv.action_space`；
- `PPOAgent` 动作缩放/裁剪；
- `ActionProcessor`；
- 运动学模型；
- 测试和文档。

更推荐让 Actor 输出 `tanh` 归一化动作，再乘以 `a_max`，并正确修正变换后的 log probability。

### 11.4 接入能耗

推荐步骤：

1. 在环境状态中维护每架无人机 SOC；
2. 每步调用 `EnergyModel.compute_flight_power()` 和 `update_soc()`；
3. 用真实 SOC 替换观测中的 `0.8`；
4. 将单步能耗写入 `info`；
5. 奖励函数读取能耗；
6. 电量不足时触发返航或动态重分配；
7. 增加能耗守恒和终止条件测试。

### 11.5 接入 CTDE

建议实现一套明确的数据流：

```text
每架 UAV 局部观测 → 共享 Actor → 每架 UAV 动作
所有局部观测拼接 → Centralized Critic → 全局价值
共享/个体奖励 → GAE → PPO 更新
```

需要避免把当前集中式联合 Actor 直接称作分散式执行。评估时每个 Actor 的输入必须不依赖其他无人机私有状态。

### 11.6 接入任务分配

高层分配器输出：

```python
{drone_id: [order_id, ...]}
```

环境根据分配结果为每架无人机维护当前目标；PPO 仅负责“飞向当前目标并避障”。新订单、低电量或故障事件触发重分配，完成订单后再推进任务队列。

## 14. 常见问题

### Q1：训练非常慢，第一回合长时间不结束

检查传入 `PPOAgent` 的 `num_epochs`。当前默认可能为 1000，应改用 `update_epochs=4`。

### Q2：评估时报 `mat1 and mat2 shapes cannot be multiplied`

Agent 的 `state_dim` 与环境返回状态不一致。多机状态维度应为 `num_uavs × 11`。

### Q3：动作 reshape 失败

Agent 的 `action_dim` 应为 `num_uavs × 3`，再 reshape 为 `(num_uavs, 3)`。

### Q4：改了 `REWARD_CONFIG`，训练奖励没有变化

基础环境奖励目前硬编码在 `AirspaceEnv._compute_reward()`，没有读取 `REWARD_CONFIG`。

### Q5：改了 `d_safe_uav`，碰撞阈值没有变化

基础环境读取的是 `d_safe`。需要先统一配置键。

### Q6：增强奖励训练一直不完成

增强训练脚本从 `info` 读取环境未提供的状态，回退值会使奖励失真。先扩展 `info` 或直接从环境属性读取并封装为稳定接口。

### Q7：不同场景的模型无法加载

UAV 数量变化会改变 Actor/Critic 输入输出维度。应使用同维度模型，或改用参数共享的局部 Actor。

### Q8：Gym 输出停止维护警告

这是依赖警告。短期可锁定兼容版本；长期应迁移到 Gymnasium 的 `reset()` 与五元组 `step()` API。
